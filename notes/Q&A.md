# 学習中の Q&A

2026-09-21〜2026-09-22 の会話で出た疑問を、話題ごとに整理したもの。コードは説明用の抜粋。アドレスや型のサイズは、現在の RISC-V 64ビット・QEMU `virt` の構成を前提にしている。

実装の手順は [0921.md](0921.md) と [0922.md](0922.md) を参照する。

## UART と文字の表示

### Q1. UART に書いた文字が、そのままターミナルに出るのはなぜ？

**QEMU が仮想 UART の出力を、ホスト側のターミナルにつないでいるから。**

```text
自作 OS が UART に 'A' を書く
    ↓
QEMU が機器への書き込みを処理する
    ↓
QEMU がターミナルに 'A' を出す
```

起動時の `-nographic` で、別ウィンドウを開かず、シリアル入出力などに今のターミナルを使っている。自作 OS 自身は、ホストのターミナルを知らない。

実機では UART の送信端子から電気信号が出る。例えば USB–UART 変換器を通して別の PC で受信し、その PC のターミナルソフトで表示する。

### Q2. `uart[]` の中身は何？ 普通の配列？

**`uart` は、UART のアドレスを指すポインタ。普通の配列を確保したものではない。** C++ ではポインタにも `[]` を使える。

```cpp
volatile unsigned char* uart =
    reinterpret_cast<volatile unsigned char*>(0x10000000);
```

`unsigned char` は1バイトなので、添字が1増えるとアクセス先が1バイト進む。

| 式 | アドレス | 今回の意味 |
|---|---|---|
| `uart[0]` | `0x10000000` | 書くと文字を送信する |
| `uart[5]` | `0x10000005` | 読むと UART の状態が返る |

```cpp
while ((uart[5] & 0x20) == 0) {
}
uart[0] = 'A';
```

`0x20` は2進数で `0010 0000`。`&` でこのビットだけを取り出し、次の文字を書ける状態か調べる。ゼロの間は待つ。このように繰り返し状態を読む方法を **ポーリング**と呼ぶ。

`[0]` や `[5]` の意味を決めているのは C++ ではなく、機器の仕様。特定のアドレスへの読み書きで機器を操作する仕組みが **MMIO**。

### Q3. `char` 型だから1文字ずつ送るの？

今の `uart_putc(char c)` は、1回で1バイトを送る。

ただし根本の理由は、**UART の送信用レジスタが1バイト単位だから**。その仕様に合わせて `unsigned char*` を使っている。

`'O'` や `'K'` は1文字1バイトなので、1回ずつ送れば表示できる。UTF-8 の日本語は1文字が複数バイトになるが、その場合も1バイトずつ順番に送る。「1バイト」と「画面上の1文字」は、いつも同じとは限らない。

### Q4. 16進数表示で `digits[...]` を使わず、数値をそのまま送ったら？

**数値と、数字を表す文字コードは別なので、期待した数字が表示されない。**

```cpp
const char* digits = "0123456789abcdef";
```

これは0〜15を `'0'`〜`'f'` に変える対応表。

| 渡す値 | 送られるバイト | 表示 |
|---|---|---|
| 数値 `3` | `0x03` | 数字の `3` にはならない |
| `digits[3]` → `'3'` | `0x33` | `3` |
| `digits[10]` → `'a'` | `0x61` | `a` |

```cpp
uart_putc(digits[(value >> shift) & 0xf]);
```

`>> shift` で目的の桁を右端に移し、`& 0xf` で4ビットを取り出す。そこで得た0〜15を `digits` で文字に変えている。

## 例外処理とアセンブリ

### Q5. 例外処理は、カーネルの各所へ一つずつ入れる力技なの？

**例外の発生は CPU が検出し、登録した共通の入口へ自動で飛ぶ。** 各処理の中に同じチェックを埋め込む必要はない。

```text
カーネルのどこかで例外が発生する
    ↓ CPU が検出する
mtvec に登録した trap_entry
    ↓
trap_handler が mcause を読んで原因を判定する
```

`ebreak` は、動作確認のためにわざと例外を起こす命令だった。普段のコードへ毎回入れるものではなく、現在は取り除いている。

一方、「その原因なら何をするか」は OS 側で実装する。今は原因と場所を表示して止まるだけ。例外から元の処理へ復帰する仕組みは、まだ作っていない。

### Q6. `csrr %0, mcause` の空白とカンマは、何を区切っている？

```text
csrr    %0, mcause
命令名   出力先, 読み取り元
```

- 空白は、命令名と引数を区切る。
- カンマは、引数同士を区切る。
- カンマの後の空白は読みやすさのため。`t0,mcause` と `t0, mcause` は同じ意味。

具体的なレジスタ名で書くなら次の形になる。

```asm
csrr t0, mcause
```

「`mcause` を読み、`t0` に入れる」という意味。ただし C++ 内で書いた次の例では、出力先はコンパイラが選ぶ。

```cpp
unsigned long cause;
asm volatile("csrr %0, mcause" : "=r"(cause));
```

| 記述 | 意味 |
|---|---|
| `csrr` | CSR（CPU の制御・状態用レジスタ）を読む |
| `%0` | コンパイラが選んだ出力先レジスタに置き換わる場所 |
| `:` | 命令の文字列と C++ 側の出力指定を区切る |
| `"=r"(cause)` | レジスタに出た結果を、C++ の変数 `cause` に受け取る |

**`%0` は0番レジスタではなく、必ず `t0` になるわけでもない。**

## リンカとメモリ初期化

### Q7. `.bss` の前後を `.` で囲むのはなぜ？

**`.` で囲む特別な構文ではない。配置の前後で、その時点のアドレスを記録している。**

```ld
__bss_start = .;
*(.bss .bss.*)
*(.sbss .sbss.*)
__bss_end = .;
```

例えば配置前の `.` が `0x80001000` で、そこから `0x1000` バイト分の領域を配置すると：

```text
__bss_start = 0x80001000
    [ 配置された領域 ]
__bss_end   = 0x80002000
```

同じ `.` でも、領域を配置するにつれて値が進む。`__bss_start` と `__bss_end` は、その前後の位置に付けた名前。

この指定だけではメモリはゼロにならない。起動コードが後で **開始位置以上、終了位置未満**の範囲へゼロを書くために使う。

## virtio のレジスタ操作

### Q8. Status レジスタで「伝える」相手は誰？

**QEMU が再現している virtio 機器側の処理。ネットワークの向こうの PC ではない。**

```text
自作 OS のドライバが Status に書く
    ↓
QEMU の virtio 機器側が受け取る
    ↓
リセットや状態の更新を行う
```

UART に書くと QEMU が送信処理をしたのと同じ考え方。

- `0`：リセットする。
- `1`：機器を見つけたと報告する。
- `1 | 2`：見つけたことに加え、ドライバが操作を担当すると報告する。

ドライバは機器を操作するコードのこと。Status は準備の進み具合を伝える場所で、そこへ値を書いてもネットワーク上にパケットが送られるわけではない。

### Q9. `regs` を `char*` にしたら、4で割らなくて済むのでは？

アドレス計算だけならそうなる。ただし **アクセス幅まで変わってしまう**。

| 型 | 添字が1増えたとき | 今回のアクセス幅 |
|---|---|---|
| `unsigned char*` | 1バイト進む | 1バイト |
| `unsigned int*` | 4バイト進む | 4バイト |

virtio の制御レジスタは32ビット単位でアクセスする仕様なので、今回32ビットの `unsigned int` を使う。

```cpp
regs[0x70 / 4] = 0;
```

これは `base + 0x70` へ4バイト幅で書く操作。`unsigned char*` で同じ場所を指定すると1バイト幅になるため、同じ操作にはならない。

なお、型のサイズは環境依存の部分もある。ここでは現在のビルド設定でのサイズを前提にしている。

### Q10. レジスタに0や1を書くだけで、ほかの配列でも下位・上位を選べるの？

**普通の配列にはその機能はない。機器側が選択値を覚え、読み出し口の内容を切り替えている。** このような方式を間接アクセスと呼ぶ。

```cpp
regs[0x14 / 4] = 0;
unsigned int low = regs[0x10 / 4];

regs[0x14 / 4] = 1;
unsigned int high = regs[0x10 / 4];
```

`regs[0]` に書くのではなく、選択用の `regs[0x14 / 4]` に書いている。

```text
選択用へ 0 を書く → 読み出し口にビット0〜31が現れる
選択用へ 1 を書く → 読み出し口にビット32〜63が現れる
```

今回のレジスタの対応表：

| 用途 | 選択する場所 | 値を読む・書く場所 |
|---|---|---|
| 機器が提供する機能を読む | `0x14` | `0x10` |
| ドライバが使う機能を書く | `0x24` | `0x20` |

すべて機器の先頭からのバイト位置。上位側を選んだ後も、機能の値を書く先は `0x20`。以前あった「`0x24` に続けて値を書く」誤記は、現在の `kernel.cpp` では修正済み。

## MAC アドレスの読み出し

### Q11. MAC は6バイトなのに、`0xfc` を4バイト単位で読んでいるのはなぜ？

**`0xfc` に入っているのは MAC アドレスではなく、設定の更新番号。** MAC は `0x100` から6バイト並んでいる。

以下の位置は、すべて機器の先頭 `base` からのバイト位置。

| 位置 | 中身 | 読み方 |
|---|---|---|
| `0xfc`〜`0xff` | 設定の更新番号 | `regs[0xfc / 4]` で4バイト読む |
| `0x100`〜`0x105` | MAC アドレス | `config[0]`〜`config[5]` を1バイトずつ読む |

```cpp
volatile unsigned char* config =
    reinterpret_cast<volatile unsigned char*>(base + 0x100);
```

MAC は1バイト単位のフィールドなので、ここは `unsigned char*` を使う。制御レジスタを読む `unsigned int*` と使い分けている。

`config` は機器側を指すポインタ。一方、`unsigned char mac[6]` は、読み出した値を保存する普通の RAM 上の配列。

### Q12. MAC 読み出しで `do while` と `for` を分けるのはなぜ？

**繰り返す目的が違うから。**

```cpp
unsigned char mac[6];
unsigned int generation;

do {
    generation = regs[0xfc / 4];

    for (int i = 0; i < 6; ++i) {
        mac[i] = config[i];
    }
} while (generation != regs[0xfc / 4]);
```

- 内側の `for`：6バイトを順番に読む。
- 外側の `do while`：途中で設定が変わったら、6バイト全部を読み直す。

もし途中で設定が変わると「古い前半と新しい後半」が混ざる可能性がある。読む前後の更新番号が同じなら採用し、違えばやり直す。

`do while` は、本体を一度実行してから継続条件を調べる。今回は比較する前に必ず一度読みたいので、この形が合っている。

読み出しの後にある別の `for` は、保存した `mac` を表示するため。読み直しの途中の値を表示しないよう、読み出しと表示を分けている。

```cpp
const char* digits = "0123456789abcdef";

uart_puts("MAC = ");
for (int i = 0; i < 6; ++i) {
    if (i != 0) {
        uart_putc(':');
    }
    uart_putc(digits[mac[i] >> 4]);
    uart_putc(digits[mac[i] & 0xf]);
}
uart_puts("\r\n");
```

1バイトを上位4ビットと下位4ビットに分け、それぞれ16進数1桁にする。実行結果は `MAC = 52:54:00:12:34:56` だった。

**修正済みの例：** MAC 表示用の `digits` が一時 `0123456789abcdrf` になっていた。今回の MAC に `e` は含まれないため表示に現れなかったが、値14の桁があると `e` の代わりに `r` が出る。現在の実コードでは `0123456789abcdef` に修正済み。

## 全体の目的と進み具合

### Q13. 全体で何を作っていて、今はどこまでできた？

**自作の TCP/IP スタックを動かすための、小さな OS を作っている。** 汎用 OS を完成させることが目的ではない。

| 段階 | このノート作成時点の状態 |
|---|---|
| QEMU で起動し、スタックを用意して C++ へ入る | 完了 |
| UART で文字・数値を表示する | 完了 |
| 例外の原因と場所を表示して停止する | 完了。復帰処理は未実装 |
| 起動時の `.bss` ゼロ化 | 完了 |
| virtio-net を発見し、使う機能を決める | 完了 |
| MAC アドレスを読む | 完了 |
| 送受信キューの3領域を用意・登録する | 完了。各8要素、まだ空のキュー |
| DRIVER_OK を設定する | 実装済み。最終ステータス表示は次回確認 |
| Ethernet フレームを送受信する | これから |
| ARP → IPv4 → ICMP で ping | その後 |
| UDP → 小さな TCP | さらにその後 |
| Rust で書き直す | 後の学習目標 |

まだネットワーク上へデータは送っていない。**virtqueue**、つまり OS と機器が共有メモリでデータの場所や処理結果を受け渡すキューは登録できた。次回は最終ステータスを確認してから、実際のデータ領域をキューへ渡す準備に進む。

当面は必要な配列をあらかじめ確保し、プロセス、ファイルシステム、ユーザー空間などは追加しない。

### Q14. 結構進んだ？

**最初の大きな山は越えた。TCP/IP 全体で見ると、土台ができた段階。**

最初は起動したかも見えなかったが、今は自分の C++ が動き、文字を出し、例外の原因と場所を調べられる。さらにネットワーク機器の情報を読めるようになった。

大きな成果は、機能の数だけでなく「追加する → 動かす → 失敗したら調べる」という環境ができたこと。キューの枠組みはできたので、これからの実際の送受信と TCP も、小さく分けて取り組む。

## 送受信キュー

### Q15. ディスクリプタって何だった？

**データの「置き場所と長さ」を機器に伝える説明書。データ本体ではない。**

```cpp
struct VirtqDesc {
    uint64_t addr;
    uint32_t len;
    uint16_t flags;
    uint16_t next;
};
```

| 項目 | 意味 |
|---|---|
| `addr` | データが置いてあるメモリアドレス |
| `len` | その領域のバイト数 |
| `flags` | 機器が読むか書くか、次へ連結するかなどの指定 |
| `next` | 連結する場合の次のディスクリプタ番号 |

例えば送信用の `tx_desc[3]` に、送るデータのアドレスと長さを書く。機器は、その情報を使ってデータ本体を読める。

```text
Available Ring に「3」を入れて公開する
    ↓
機器が tx_desc[3] を読む
    ↓
addr が指す場所から len バイトを読む
```

Ring は「どの説明書を使うか」、ディスクリプタは「どのデータを使うか」を伝える。

### Q16. Available Ring は何？

**OS が機器へ渡す、処理してほしいディスクリプタ番号の一覧。**

| 場所 | 入っているもの |
|---|---|
| データ用メモリ | 実際に送受信するデータ |
| ディスクリプタ | データの場所・長さ・扱い方 |
| Available Ring | 処理してほしいディスクリプタの番号 |

```cpp
struct VirtqAvail {
    uint16_t flags;
    uint16_t idx;
    uint16_t ring[QUEUE_SIZE];
};
```

`ring` が番号の一覧、`idx` が追加の進み具合を示すカウンタ。配列の位置は `idx % QUEUE_SIZE` で求め、最後まで来たら先頭に戻るため Ring（輪）と呼ぶ。

受信の場合は「この空き領域へ届いたデータを書いて」と機器へ渡す一覧になる。領域を作っただけでは依頼にはならず、ディスクリプタの準備、番号の追加、`idx` の更新などが必要。

機器が処理中のデータやディスクリプタを、先頭に戻ったからといって勝手に上書きしてはいけない。完了は Used Ring で確認する。

### Q17. 今日、どこまでできれば順調？ 実際にはどこまで進んだ？

目標は次の3つだった。

1. Available Ring を用意する。
2. Used Ring を用意する。
3. キューを機器に登録し、初期化完了を通知する。

**終了時点では、3つともコードを追加した。** キュー登録までは実行できたと確認している。最後の DRIVER_OK 設定もソースにあるが、最終ステータス `0x0f` の実際の表示はまだ会話で確認していないため、次回の最初に確認する。

今日はパケット送信や ping まで進む予定ではなかった。キューの役割を理解し、領域を用意して機器へ登録するところまでが一区切り。

### 補足：Used Ring は Available Ring とどう違う？

**依頼を書くのは OS、完了を書くのは機器。**

| 領域 | 動作中に書く側 | 読む側 | 内容 |
|---|---|---|---|
| Available Ring | OS | 機器 | 処理してほしいディスクリプタ番号 |
| Used Ring | 機器 | OS | 完了した番号と、機器が書き込んだバイト数 |

```cpp
struct VirtqUsedElem {
    uint32_t id;
    uint32_t len;
};
```

`id` は完了したディスクリプタ番号（連結時は先頭）、`len` は機器がデータ領域へ書いたバイト数。送信したバイト数ではない。

現在の8要素構成では、ディスクリプタ表128バイト、Available Ring 20バイト、Used Ring 68バイト。これは領域のサイズであり、送受信できるパケットのバイト数とは別。

### 補足：QueueReady と DRIVER_OK は同じ？

**QueueReady は各キュー、DRIVER_OK は機器全体の準備完了。**

- キュー番号を選び、要素数と3領域のアドレスを登録して、そのキューの QueueReady を1にする。
- RX と TX の登録後、Status に DRIVER_OK のビット `4` を追加する。

```cpp
regs[0x70 / 4] = regs[0x70 / 4] | 4;
```

今回の期待値は `1 | 2 | 8 | 4 = 15 = 0x0f`。キューはまだ空なので、これだけではデータは送受信されない。`0x0f` は「パケットが届いた」という結果ではない。

### 補足：アドレスをなぜ2つのレジスタに分けて書く？

アドレスは64ビット、機器の制御レジスタは32ビット幅だから。

```cpp
regs[0x80 / 4] = static_cast<uint32_t>(desc_addr);
regs[0x84 / 4] = static_cast<uint32_t>(desc_addr >> 32);
```

最初に下位32ビット、次に上位32ビットを書く。`>> 32` は上位側を右端へ移す操作。

`uintptr_t` はポインタの値を保持できる整数型。今の構成ではポインタの値を物理アドレスとして使えるが、アドレス変換を導入する場合は別途考える必要がある。

### 補足：`volatile` があるのに、なぜ `fence` も書く？

役割が違う。

- `volatile`：機器との読み書きを、コンパイラが不要と判断して省くことなどを防ぐ。
- `fence`：CPU のメモリや機器へのアクセス順序をそろえる。
- インラインアセンブリの `"memory"`：コンパイラ側にもメモリ操作の並べ替えを制限するための指定。

```cpp
asm volatile("fence iorw, iorw" ::: "memory");
regs[0x44 / 4] = 1;
```

今回は、準備の書き込みが機器へのキュー有効化通知より後にならないようにするために入れた。実際の送受信で共有メモリを扱う際にも、順序の考慮が必要になる。
