## 1. mepc と実際の命令を照合する

機械語をアセンブリ表記に戻して読むことを **逆アセンブル**と呼ぶ。

```sh
llvm-objdump-21 -d kernel.elf
```

当時の出力には次の行があった。

```text
8000019a: 9002    ebreak
```

| 部分 | 意味 |
|---|---|
| `8000019a` | 命令のアドレス |
| `9002` | 機械語。この例では16ビットの圧縮命令 |
| `ebreak` | 命令の名前 |

実行時に表示した `mepc = 0x000000008000019a` と一致することを確認した。先頭のゼロは数値に影響しない。

これで CPU が記録したアドレスから例外を起こした命令を探せるようになった。コードを追加すると配置が変わるため、アドレスは固定ではない。比較には、QEMU で実行したものと同じ `kernel.elf` を使う。

## 2. .bss の範囲に名前を付ける

`.bss` はゼロ初期化が必要な変数などのための領域。今回のスタックもここに確保している。起動時に自分たちでゼロにできるよう、`linker.ld` に両端のシンボルを追加した。シンボルはアドレスなどに付ける名前。

```ld
.bss : {
    __bss_start = .;
    *(.bss .bss.*)
    *(.sbss .sbss.*)
    __bss_end = .;
}
```

**`.` で領域を囲む特別な構文ではない。配置の前後で、その時点のアドレスを記録している。**

例えば配置前の `.` が `0x80001000` で、配置する領域の合計が `0x1000` バイトだった場合：

```text
__bss_start = 0x80001000
    [ ゼロにする範囲 ]
__bss_end   = 0x80002000
```

対象は `__bss_start` 以上、`__bss_end` 未満。終了位置そのものは含めない。領域の配置に応じて `.` が進むので、同じ記号でも値は変わる。

この指定は範囲に名前を付けるだけで、実行時にゼロを書く処理ではない。

```sh
make
readelf -s kernel.elf
```

シンボル一覧に `__bss_start` と `__bss_end` があることを確認した。

## 3. 起動時に1バイトずつゼロを書く

`boot.S` の `_start` の先頭に、範囲内をゼロで埋めるループを追加した。

```asm
_start:
    # Clear BSS.
    la t0, __bss_start
    la t1, __bss_end

clear_bss:
    bgeu t0, t1, clear_bss_done
    sb zero, 0(t0)
    addi t0, t0, 1
    j clear_bss

clear_bss_done:
    # Set the stack pointer.
    la sp, stack_top

    # Set the trap entry.
    la t0, trap_entry
    csrw mtvec, t0

    call kernel_main
```

| 命令 | 役割 |
|---|---|
| `la t0, __bss_start` | 書き込み先を先頭にする |
| `la t1, __bss_end` | 終了位置を保持する |
| `bgeu t0, t1, clear_bss_done` | 符号なし比較で `t0 >= t1` なら終了する |
| `sb zero, 0(t0)` | `t0` の指す場所へ1バイトのゼロを書く |
| `addi t0, t0, 1` | 次の1バイトへ進む |
| `j clear_bss` | ループの先頭へ戻る |

`zero` は常にゼロを返すレジスタ。`0(t0)` は「`t0` のアドレスから0バイト先」という指定。

スタックもこの範囲にあるので、**スタックを使用して関数を呼ぶ前にゼロ化する**。このループはレジスタだけで動き、関数呼び出しをしない。

## 4. QEMU が用意したゼロと、自分で書いたゼロを区別する

単に起動できただけでは、ゼロ化の確認にはならない。一時的な変数へ先に `0x5a` を書き、ループ後にゼロになるか確かめた。

`kernel.cpp` の関数外に、次の変数を置いた。

```cpp
extern "C" {
    volatile unsigned char bss_probe;
}
```

- 初期値を書かないグローバル変数なので、今回の構成では `.bss` または `.sbss` に置かれる。
- `extern "C"` はアセンブリから `bss_probe` という名前で参照するため。
- `volatile` は確認時に実際のメモリの値を読ませるため。

`_start` のゼロ化ループより前に追加した確認コード：

```asm
    # Set a test value.
    la t0, bss_probe
    li t1, 0x5a
    sb t1, 0(t0)
```

`li` は数値をレジスタに入れる指定。このあと既存のゼロ化ループを通り、`kernel_main` で値を表示した。

```cpp
uart_puts("bss_probe = ");
uart_put_hex(bss_probe);
uart_puts("\r\n");
```

```text
bss_probe = 0x0000000000000000
```

先に書いた `0x5a` が、このループによってゼロになることを確認した。これは確認用の1バイトに対する動作確認であり、全メモリの検査ではない。

確認後、変数・事前の書き込み・表示の3か所を削除した。ゼロ化ループは残した。また、通常起動へ戻すため、`kernel_main` の `asm volatile("ebreak");` も削除した。トラップハンドラは今後の異常検出用に残している。

## 5. QEMU にネットワーク機器を追加する

使用する機器は **virtio-net**。仮想環境向けのネットワーク機器で、今回は MMIO 経由で操作する。

メモリは当面、必要なサイズの配列をあらかじめ用意する方針。動的メモリ確保や大きなメモリ管理機構はまだ実装しない。

`Makefile` の起動部分：

```makefile
.PHONY: run
run: kernel.elf
	qemu-system-riscv64 \
		-machine virt -bios none -smp 1 -m 128M \
		-nographic -kernel kernel.elf \
		-global virtio-mmio.force-legacy=false \
		-netdev user,id=net0 \
		-device virtio-net-device,netdev=net0
```

| 追加指定 | 役割 |
|---|---|
| `-global virtio-mmio.force-legacy=false` | 古い互換方式ではなく、新しい MMIO 方式を使う |
| `-netdev user,id=net0` | 管理者権限なしで使える QEMU 側のネットワーク接続を作る |
| `-device virtio-net-device,netdev=net0` | ネットワーク機器を追加し、その接続につなぐ |

この時点で `Hello!` が出ても、OS のネットワーク処理が完成したわけではない。追加した機器を使うコードは、ここから自分たちで書く。

## 6. MMIO を読んでネットワーク機器を探す

QEMU の `virt` の既知の配置を使い、`0x10001000` から `0x1000` バイト間隔にある8か所を調べた。任意のアドレスを手当たり次第に読む方法ではない。この配置に依存する部分は、実機へ移す際には見直す。

```cpp
unsigned long find_virtio_net() {
    for (unsigned long slot = 0; slot < 8; ++slot) {
        unsigned long base = 0x10001000 + slot * 0x1000;
        volatile unsigned int* regs =
            reinterpret_cast<volatile unsigned int*>(base);

        if (regs[0] == 0x74726976 &&
            regs[1] == 2 &&
            regs[2] == 1) {
            return base;
        }
    }
    return 0;
}
```

最初は関数内でアドレスを表示する `void find_virtio_net()` を作った。その後、初期化に利用できるよう、見つかったアドレスを返す形に変えた。上は変更後のコード。

| 読む式 | 先頭からのバイト位置 | 意味・期待する値 |
|---|---|---|
| `regs[0]` | `0x00` | 識別値 `0x74726976`：virtio である |
| `regs[1]` | `0x04` | バージョン `2`：新しい MMIO 方式である |
| `regs[2]` | `0x08` | 機器 ID `1`：ネットワーク機器である |

`regs` は今回32ビットである `unsigned int` へのポインタ。**1バイトずつではなく、4バイト単位で読み出している。** `reinterpret_cast` は数値のアドレスをアクセス用のポインタとして扱うために使う。

見つからなければ `0` を返す約束にした。探索範囲にアドレス `0` はないため区別できる。

```cpp
unsigned long net_base = find_virtio_net();

if (net_base == 0) {
    uart_puts("virtio-net not found\r\n");
} else {
    uart_puts("virtio-net at ");
    uart_put_hex(net_base);
    uart_puts("\r\n");
    virtio_net_begin(net_base);
}
```

この環境での表示は `virtio-net at 0x0000000010008000`。常にこのスロットにあると決めつけず、見つけた値を使用する。

## 7. Status レジスタで初期化の進み具合を伝える

**ドライバ**は機器を操作するコードのこと。機器の先頭から `0x70` バイト先にある Status レジスタへ初期化の進み具合を書く。

```cpp
void virtio_net_begin(unsigned long base) {
    volatile unsigned int* regs =
        reinterpret_cast<volatile unsigned int*>(base);

    // Reset the device.
    regs[0x70 / 4] = 0;
    while (regs[0x70 / 4] != 0) {
    }

    // ACKNOWLEDGE
    regs[0x70 / 4] = 1;

    // ACKNOWLEDGE | DRIVER
    regs[0x70 / 4] = 1 | 2;

    uart_puts("virtio status = ");
    uart_put_hex(regs[0x70 / 4]);
    uart_puts("\r\n");
}
```

1. `0` を書き、機器をリセットする。
2. 読み戻した値が `0` になるまで待つ。
3. `1`：機器を発見したことを伝える。
4. `1 | 2`：発見済みのビットを残して、ドライバが操作を担当することを伝える。

`|` はビットを組み合わせる演算。`1 | 2` は `3` になる。表示でも `virtio status = 0x0000000000000003` を確認した。

伝える相手は、ネットワークの向こうの PC ではなく、**QEMU 内の virtio 機器の処理**。

```text
自作 OS が Status レジスタに書く
    ↓
QEMU の機器側の処理が書き込みを受け取る
    ↓
リセットや状態の更新を行う
```

まだネットワーク上へパケットを送っているわけではない。

### なぜ char* にせず、毎回4で割るのか

virtio の制御レジスタには「32ビット単位で読み書きする」という仕様がある。今回の `unsigned int*` なら添字1つで4バイト進み、アクセス幅も4バイトになる。

```text
regs[0x70 / 4]
    → base + (0x70 / 4) × 4
    → base + 0x70
```

`unsigned char*` にすればアドレス計算の `/ 4` は不要だが、アクセス幅が1バイトになってしまう。アドレスが同じでもアクセス幅が違えば、同じ機器操作とは限らない。

## 8. 機器が対応する機能を読み出す

**機能ビット**は、対応している機能を1ビットずつ表すもの。今回は下位32ビットと上位32ビットを切り替えて読んだ。次のコードは `virtio_net_begin` の中へ追加したもの。

```cpp
regs[0x14 / 4] = 0;
unsigned int features_low = regs[0x10 / 4];

regs[0x14 / 4] = 1;
unsigned int features_high = regs[0x10 / 4];

uart_puts("features low = ");
uart_put_hex(features_low);
uart_puts("\r\n");

uart_puts("features high = ");
uart_put_hex(features_high);
uart_puts("\r\n");
```

| レジスタのバイト位置 | 用途 |
|---|---|
| `0x14`：DeviceFeaturesSel | どの32ビットを読むか選択する |
| `0x10`：DeviceFeatures | 選択した32ビットを読み出す |

同じ読み出し口の内容を、選択用レジスタで切り替える **間接アクセス**という仕組み。

```text
0x14 へ 0 を書く → 0x10 から全体のビット0〜31を読む
0x14 へ 1 を書く → 0x10 から全体のビット32〜63を読む
```

普通の配列の機能ではなく、機器側が選択値を覚えて応答を変えている。`regs[0]` に `0` を書くという意味ではない。

得られた値は次のとおり。実際の表示にあった `featurtes` は、ノートでは `features` に直している。

```text
features low = 0x0000000030bf8024
features high = 0x0000000000000101
```

`uart_put_hex` は16桁固定なので、32ビットの値でも先頭にゼロが付く。

今回使う機能は、必要最小限の次の2つ。

| 機能 | ビット位置 | 判定 |
|---|---|---|
| `VIRTIO_NET_F_MAC` | 全体のビット5＝下位のビット5 | `features_low & 0x20` |
| `VIRTIO_F_VERSION_1` | 全体のビット32＝上位のビット0 | `features_high & 0x01` |

MAC アドレスは Ethernet の送信元・宛先を表す6バイトのアドレス。MAC 機能は機器が提供する MAC アドレスを読めることを示す。VERSION_1 は virtio 1.0 以降の方式への対応を示す。

```text
0x30bf8024 & 0x20 = 0x20
0x00000101 & 0x01 = 0x01
```

両方とも対応している。ほかの機能は今は選ばない。

## 9. 使う機能を選び、受け入れられたか確認する

機器が提供する機能のうち、自分のドライバが使うものを伝えることを **機能交渉**と呼ぶ。対応している機能を全部有効にするのではなく、実装できるものだけ選ぶ。

次は `virtio_net_begin` に追加した機能交渉のコード。書き込み先の誤記は実コードでも修正済み。以下の抜粋では表示文字列の誤字も整えている。

```cpp
if ((features_low & 0x20) == 0 ||
    (features_high & 0x01) == 0) {
    uart_puts("Required features missing\r\n");
    regs[0x70 / 4] = regs[0x70 / 4] | 128;
    return;
}

// Select MAC and VERSION_1.
regs[0x24 / 4] = 0;
regs[0x20 / 4] = 0x20;

regs[0x24 / 4] = 1;
regs[0x20 / 4] = 0x01;

// Set FEATURES_OK.
regs[0x70 / 4] = 1 | 2 | 8;

unsigned int status = regs[0x70 / 4];
if ((status & 8) == 0) {
    uart_puts("Features rejected\r\n");
    regs[0x70 / 4] = status | 128;
    return;
}

uart_puts("Features accepted\r\n");
```

| レジスタのバイト位置 | 用途 |
|---|---|
| `0x24`：DriverFeaturesSel | 書く機能の下位・上位を選択する |
| `0x20`：DriverFeatures | 選択した側へ、使う機能ビットを書く |
| `0x70`：Status | 初期化の進み具合を書く・読む |

読む側は `0x14` と `0x10`、選んだ機能を伝える側は `0x24` と `0x20`。それぞれ「選択用」と「値用」のペアになっている。

| Status の値・ビット | 意味 |
|---|---|
| `1`：ACKNOWLEDGE | 機器を見つけた |
| `2`：DRIVER | ドライバが操作を担当する |
| `8`：FEATURES_OK | 使う機能の選択が完了した |
| `128`：FAILED | 初期化を断念した |
| `4`：DRIVER_OK | 機器を動作可能にする最後の準備完了通知。この段階ではまだ設定せず、キュー登録後に設定する |

`FEATURES_OK` を書いた後は必ず読み直す。機器が選択を受け入れなければ、そのビットはゼロになる。失敗した場合は `FAILED` を立て、`return` で初期化を中断する。

### 学習中に直した書き込み先の誤り

以前のノートと `kernel.cpp` には、上位の機能を設定する箇所が次のように書かれていた。以下は修正前の例。

```cpp
regs[0x24 / 4] = 1;
regs[0x24 / 4] = 0x01;
```

`1` と `0x01` は同じ値なので、これは上位側を2回選択しているだけ。**上位の機能ビットの値をまだ書いていない。** 2行目の書き込み先は、選択用の `0x24` ではなく値用の `0x20` にする必要がある。

その後、2行目を `regs[0x20 / 4] = 0x01;` に修正し、再実行できたと確認した。現在のソースにも修正が反映されている。表示の誤字 `featurtes` と `missin` は残っているが、こちらは表示だけの問題。

## 10. MAC アドレスを読み出す

機能交渉の成功後、機器の先頭から `0x100` バイト先にある6バイトの MAC アドレスを読んだ。

```cpp
volatile unsigned char* config =
    reinterpret_cast<volatile unsigned char*>(base + 0x100);
unsigned char mac[6];
unsigned int generation;

do {
    generation = regs[0xfc / 4];
    for (int i = 0; i < 6; ++i) {
        mac[i] = config[i];
    }
} while (generation != regs[0xfc / 4]);

const char* digits = "0123456789abcdef";
uart_puts("MAC = ");
for (int i = 0; i < 6; ++i) {
    if (i != 0) {
        uart_putc(':');
    }
    uart_putc(digits[mac[i] >> 4]);
    uart_putc(digits[mac[i] & 0xf]);
}
uart_puts("\r\n");
```

| 機器の先頭からの位置 | 中身 | アクセス幅 |
|---|---|---|
| `0xfc`〜`0xff` | 設定の更新番号（ConfigGeneration） | 4バイト |
| `0x100`〜`0x105` | MAC アドレス | 1バイトずつ6回 |

`0xfc` に MAC が入っているわけではない。`regs` は32ビットの制御レジスタ用、`config` は1バイト単位の MAC フィールド用に使い分ける。`mac` は、読み取った値を置く普通の RAM 上の配列。

内側の `for` は6バイトを読むため、外側の `do while` は途中で設定が変わったら全部読み直すため。更新番号を前後で比べることで、異なる時点の設定が混ざるのを避ける。その後の表示用 `for` は、読み終わった配列から1バイトを16進数2桁へ変換する。

確認した表示：

```text
MAC = 52:54:00:12:34:56
```

MAC 表示用 `digits` の末尾が一時 `abcdrf` になっていたが、現在は `abcdef` に修正済み。今回の MAC には `e` の桁がないため、この誤字は表示に現れなかった。

## 11. 送受信キューの最大サイズを調べる

**virtqueue** は、OS と機器が共有メモリでデータの場所や処理結果を受け渡す仕組み。今回はキュー0を受信（RX）、キュー1を送信（TX）に使う。

```cpp
regs[0x30 / 4] = 0;
unsigned int rx_max = regs[0x34 / 4];

regs[0x30 / 4] = 1;
unsigned int tx_max = regs[0x34 / 4];

uart_puts("RX queue max = ");
uart_put_hex(rx_max);
uart_puts("\r\n");
uart_puts("TX queue max = ");
uart_put_hex(tx_max);
uart_puts("\r\n");
```

`0x30` の QueueSel で対象を選び、`0x34` の QueueNumMax を読む。ここも「選択用と値用」のレジスタを使う間接アクセス。

```text
RX queue max = 0x0000000000000400
TX queue max = 0x0000000000000400
```

`0x400` は1024。**バイト数ではなく、ディスクリプタの個数の上限**。`0` なら利用できないキューを意味する。最大数すべてを使う必要はないので、まず各8個にした。

## 12. ディスクリプタ表を用意する

**ディスクリプタ**は、データの「メモリ上の場所・長さ・扱い方」を機器へ伝える説明書。データ本体ではない。

```cpp
#include <stdint.h>

struct VirtqDesc {
    uint64_t addr;
    uint32_t len;
    uint16_t flags;
    uint16_t next;
};

static_assert(sizeof(VirtqDesc) == 16,
              "VirtqDesc must be 16 bytes");
constexpr unsigned int QUEUE_SIZE = 8;

alignas(16) VirtqDesc rx_desc[QUEUE_SIZE] = {};
alignas(16) VirtqDesc tx_desc[QUEUE_SIZE] = {};
```

| 項目 | 大きさ | 意味 |
|---|---|---|
| `addr` | 8バイト | データの物理アドレス |
| `len` | 4バイト | データ領域の長さ |
| `flags` | 2バイト | 機器が読むか書くか、連結するかなどの指定 |
| `next` | 2バイト | 連結する場合の次のディスクリプタ番号 |

- `struct` は複数の項目をまとめた型を定義する。
- `uint64_t` などは幅が明確な符号なし整数型。機器と共有するデータ形式に合わせて使う。
- `static_assert` はコンパイル時の確認。型の大きさが想定と違えばビルドを止める。
- `constexpr` はコンパイル時に決まる定数。要素数の8に名前を付けた。
- `alignas(16)` は配列の先頭を16バイト境界にそろえる指定。1要素のサイズだけでなく、表の開始位置にも要件がある。
- `= {}` は全項目をゼロ初期化する。関数外に確保し、今回の構成では `.bss` の起動処理でゼロになる。

関数外に置くことで、初期化関数から戻った後も機器と共有する領域が残る。

```sh
make
readelf -s kernel.elf
```

当時の出力では `rx_desc` が `0x80001680`、`tx_desc` が `0x80001700` で、両方128バイトだった。これは16バイト×8個分。どちらも16バイト境界にそろっている。後から領域を追加すると、アドレスは変わることがある。

## 13. Available Ring：OS から機器への依頼一覧

Available Ring には、処理してほしい **ディスクリプタの番号**を入れる。

```cpp
struct VirtqAvail {
    uint16_t flags;
    uint16_t idx;
    uint16_t ring[QUEUE_SIZE];
};

alignas(2) VirtqAvail rx_avail = {};
alignas(2) VirtqAvail tx_avail = {};
```

| 項目 | 役割 |
|---|---|
| `flags` | 通知に関する指定。今はゼロ |
| `idx` | OS が追加するたびに増やすカウンタ |
| `ring` | 機器へ渡すディスクリプタ番号の配列 |

例えば送信時に `ring[0] = 3` と入れるなら、機器へ `tx_desc[3]` を使ってほしいという意味。実際に公開するときは、内容の準備に加えて `idx` の更新やアクセス順序の制御も必要になる。今回は領域の確保まで。

```text
送信データ本体
    ↑ addr で指す
ディスクリプタ tx_desc[3]
    ↑ 番号3で指定する
Available Ring
```

Ring（輪）という名前は、配列の最後まで来たら先頭に戻り、枠を再利用することに由来する。配列の位置は `idx % QUEUE_SIZE` で求める。`idx` は増え続け、16ビットの範囲を超えると折り返す。処理中のデータやディスクリプタを勝手に上書きしてよいわけではない。

受信では「届いたデータをこの空き領域に書いて」という依頼になる。

```text
flags 2 + idx 2 + ring 2×8 = 20バイト
```

`readelf -s kernel.elf` で20バイトになっていることを確認した。現在は追加の通知制御機能 EVENT_IDX を選んでいないので、その機能用の項目は含めていない。

## 14. Used Ring：機器から OS への完了一覧

Used Ring は、機器が処理を終えたディスクリプタを OS に返すための一覧。

```cpp
struct VirtqUsedElem {
    uint32_t id;
    uint32_t len;
};

struct VirtqUsed {
    uint16_t flags;
    uint16_t idx;
    VirtqUsedElem ring[QUEUE_SIZE];
};

alignas(4) volatile VirtqUsed rx_used = {};
alignas(4) volatile VirtqUsed tx_used = {};

static_assert(sizeof(VirtqUsedElem) == 8,
              "VirtqUsedElem must be 8 bytes");
static_assert(sizeof(VirtqUsed) == 68,
              "VirtqUsed must be 68 bytes");
```

| 項目 | 役割 |
|---|---|
| `flags` | 通知に関する指定 |
| `idx` | 機器が完了情報を追加するたびに増やすカウンタ |
| `ring[i].id` | 完了したディスクリプタ番号。連結時は先頭の番号 |
| `ring[i].len` | 機器がデータ領域へ書き込んだバイト数 |

`len` は送信したバイト数ではない。受信時には、機器が何バイト書き込んだか分かる。

```text
1要素 = id 4 + len 4 = 8バイト
全体 = flags 2 + idx 2 + ring 8×8 = 68バイト
```

ここも EVENT_IDX 用の項目は含めない。`volatile` は機器側で更新される値を読み直すために使う。ただし、それだけで共有メモリのアクセス順序が保証されるわけではない。

これで RX と TX それぞれに、次の3種類の領域がそろった。

| 領域 | 1キュー分のサイズ | 先頭の整列 |
|---|---:|---:|
| Descriptor Table | 128バイト | 16バイト |
| Available Ring | 20バイト | 2バイト |
| Used Ring | 68バイト | 4バイト |

## 15. キューのメモリアドレスを機器に登録する

型や配列を作っただけでは、機器はその場所を知らない。MMIO レジスタに各領域の物理アドレスを登録する。

RX と TX で手順が同じなので、共通の `setup_virtqueue` を作った。

```cpp
bool setup_virtqueue(volatile unsigned int* regs,
                     unsigned int queue,
                     VirtqDesc* desc,
                     VirtqAvail* avail,
                     volatile VirtqUsed* used) {
    regs[0x30 / 4] = queue;
    if (regs[0x44 / 4] != 0) {
        return false;
    }
    if (regs[0x34 / 4] < QUEUE_SIZE) {
        return false;
    }

    regs[0x38 / 4] = QUEUE_SIZE;

    uint64_t desc_addr = reinterpret_cast<uintptr_t>(desc);
    uint64_t avail_addr = reinterpret_cast<uintptr_t>(avail);
    uint64_t used_addr = reinterpret_cast<uintptr_t>(used);

    // Descriptor table.
    regs[0x80 / 4] = static_cast<uint32_t>(desc_addr);
    regs[0x84 / 4] = static_cast<uint32_t>(desc_addr >> 32);

    // Available ring.
    regs[0x90 / 4] = static_cast<uint32_t>(avail_addr);
    regs[0x94 / 4] = static_cast<uint32_t>(avail_addr >> 32);

    // Used ring.
    regs[0xa0 / 4] = static_cast<uint32_t>(used_addr);
    regs[0xa4 / 4] = static_cast<uint32_t>(used_addr >> 32);

    // Publish the queue.
    asm volatile("fence iorw, iorw" ::: "memory");
    regs[0x44 / 4] = 1;

    return regs[0x44 / 4] == 1;
}
```

登録の順序：

1. キュー番号を選ぶ。
2. 未使用であり、8要素を使える容量があることを確認する。
3. 使用する要素数を通知する。
4. 3種類の領域のアドレスを登録する。
5. 準備の書き込み順序をそろえ、QueueReady を1にする。
6. QueueReady を読み戻し、登録状態を確認する。

| レジスタの位置 | 用途 |
|---|---|
| `0x30` | QueueSel：対象キューの選択 |
| `0x34` | QueueNumMax：最大要素数 |
| `0x38` | QueueNum：実際に使う要素数 |
| `0x80` / `0x84` | Descriptor Table のアドレスの下位 / 上位 |
| `0x90` / `0x94` | Available Ring のアドレスの下位 / 上位 |
| `0xa0` / `0xa4` | Used Ring のアドレスの下位 / 上位 |
| `0x44` | QueueReady：各キューの有効化 |

`uintptr_t` はポインタの値を保持できる符号なし整数型。今回の構成ではアドレス変換を使っていないため、このアドレスを機器へ渡せる。将来アドレス変換を導入する場合は、単純なキャストだけで物理アドレスになるとは限らない。

アドレスは64ビットだがレジスタは32ビットなので、2回に分けて書く。`static_cast<uint32_t>(addr)` は下位32ビット、`addr >> 32` を同じ型へ変換したものは上位32ビット。

`fence iorw, iorw` はメモリ・機器へのアクセス順序をそろえる命令。準備の書き込みがキュー有効化より後にならないようにしている。`"memory"` はコンパイラ側にもメモリ操作の並べ替えを制限するための指定。`volatile` とは役割が違う。

`virtio_net_begin` の末尾で両方を登録する。

```cpp
if (!setup_virtqueue(regs, 0, rx_desc, &rx_avail, &rx_used) ||
    !setup_virtqueue(regs, 1, tx_desc, &tx_avail, &tx_used)) {
    uart_puts("Queue setup failed\r\n");
    regs[0x70 / 4] = regs[0x70 / 4] | 128;
    return;
}
uart_puts("Queue registered\r\n");
```

配列名 `rx_desc` はここでは先頭要素へのポインタとして渡される。`&rx_avail` や `&rx_used` は、構造体の変数のアドレスを渡す指定。

`||` は左から判定し、RX 登録が失敗したら TX の登録には進まない。どちらか失敗したら FAILED を立てて終了する。ユーザーから、登録処理を実行できたとの報告があった。

## 16. 機器全体へ初期化完了を通知する

各キューの QueueReady とは別に、機器全体の Status へ DRIVER_OK を設定する。

```cpp
// Set DRIVER_OK.
asm volatile("fence iorw, iorw" ::: "memory");
regs[0x70 / 4] = regs[0x70 / 4] | 4;

uart_puts("virtio final status = ");
uart_put_hex(regs[0x70 / 4]);
uart_puts("\r\n");
```

既存のビットを残し、`4` を追加する。期待する最終値は次のとおり。

```text
ACKNOWLEDGE | DRIVER | FEATURES_OK | DRIVER_OK
     1      |   2    |      8      |     4
                     = 15 = 0x0f
```

```text
virtio final status = 0x000000000000000f
```

**この最後の表示は期待値。** 今日の終了時点のソースには処理が入っているが、会話では最後の実行結果そのものはまだ共有されていない。ノート更新のための再ビルド・実行も行っていない。

キューはまだ空で、Available Ring の `idx` はゼロ。機器に処理を依頼するデータは渡していない。DRIVER_OK の設定は、実際にパケットを送受信できた証明ではない。

## 17. 今日の到達点と次回の再開位置

今日の目標だった「Available Ring、Used Ring、機器への登録と初期化完了通知」までコードを書いた。

| 項目 | 状態 |
|---|---|
| `.bss` のゼロ化 | 実装し、確認用変数で動作確認済み |
| virtio-net の検出・機能交渉 | 修正を含めて確認済み |
| MAC 読み出し | `52:54:00:12:34:56` を確認済み |
| キュー容量 | RX / TX とも最大1024要素を確認済み |
| キューのメモリ領域 | 各8要素で用意済み |
| キュー登録 | 実装・実行報告あり |
| DRIVER_OK 通知 | 実装済み。最終ステータスの表示確認は再開時に行う |

